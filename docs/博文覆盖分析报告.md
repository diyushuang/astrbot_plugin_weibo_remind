## 四、机制：怎么做到「覆盖所有博文」

### 1. 分类先行（`coverage.classify_post`）

按 建议反馈 → 声明打假 → 排期公告 → 日常 的优先级判形态（顺序即优先级的理由：
打假博文里同时有「行程」「通知」等排期词，排期判定放前面会误判）。
排期公告类再分为「结构化时间标记」（⏰、【HHMM】、X月X日、HH:MM）与关键词两类证据。

### 2. 分层解析 + 独立容错

结构化层（排期体结构） > 纯数字层（1030） > jionlp 层（自然语言）；
三层各自 `_safe_engine` 容错，单层异常只丢该层结果。

### 3. 覆盖自检闭环

- 每条博文记录形态 / 处理结果 / 处置原因（`coverage.json`，跨重启累计）
- 排期类但没建出任务的样本追加 `uncovered.jsonl`
- `微博提醒 覆盖` 查看形态分布、处理结果、覆盖率与最近待补样本

**这就是「覆盖所有博文」的落地方式**：不是保证每一条都能解析出时间，而是保证
每一条都有明确归类与处置，且没覆盖到的会自己浮出来可供补规则。

## 五、本轮修复的真实缺陷

| 缺陷 | 症状 | 根因 | 修复 |
| --- | --- | --- | --- |
| 【1700】被读成公元 1700 年 | Windows 上 `OSError: [Errno 22]`，整轮解析中断 | jionlp 把无分隔四位数字解为年份，`fromtimestamp` 不支持 1970 前时间 | 喂 jionlp 前掩码括号时刻；年份合理性过滤（基准年 -1~+3）；时间戳安全转换 |
| 20 条噪音会被推给群友 | 建议博/打假声明被判「疑似含时间」 | 判据是「有没有时间信号」，而这些博文含「月」「行程」 | 改为按博文形态决定是否推原文 |
| 紧凑日期漏检 | 8 条排期博文整条不建提醒 | `0711`/`【623】`/`12.03` 不被识别为日期，后续时刻失去日期归属 | 结构化层加紧凑日期（须与排期词同段） |
| 次日排期被误判为已过 | 「7:28 发布…」发布于 16:01，被判已过去 | 裸时刻归到发布当天 | 排期词出现时裸时刻顺延到次日 |
| 同日重复候选 | 「明日10点」同时产出 09:00 与 10:00 | 全天日期候选未与精确候选去重 | 同日有精确候选时丢弃纯日期候选 |
| 覆盖率统计失真 | 同一条既进「待补样本」又进「已推原文」 | 判定顺序导致两次记录 | 每条只记一次处理结果 |

## 六、已知边界与后续

1. **深翻历史需要登录**：更高覆盖需要 `custom_cookie`；填入后重新跑一次
   `.workbuddy/corpus/` 的抓取脚本即可扩语料到 288 条。
2. **周期表达只提醒最近一次**：`每周五晚8点` 不自动续期。
3. **纯数字无上下文不猜**：`1030` 歧义时不建任务（避免把编号/价格当时间）。
4. **持续提升路径**：运行期看 `微博提醒 覆盖` → 若出现待补样本，照 `uncovered.jsonl`
   里的原文补规则 → 补进 `tests/corpus/weibo_posts.json` 做回归。
